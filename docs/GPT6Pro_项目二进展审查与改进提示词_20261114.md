## 2. 已核对的事实与本轮目标

- **训练配置。** 学生 `deepseek-ai/DeepSeek-R1-Distill-Qwen-1.5B`，数学教师 `hbx/JustRL-DeepSeek-1.5B`，代码教师 `Fate-Zero/Archer2.0-Code-1.5B-Preview`。具体 revision 以源码与 run identity 为准。单张 RTX PRO 6000 Blackwell G4，LoRA，62 个更新，数学与代码交替，各 31 步；每步 32 prompts × 4 responses，最多 16,384 token，温度 1.0，生成并发 4，每微批 24,576 个 padded token，AdamW 固定学习率 1e-5，共同 support 为 151,665。数据 v5 有 2,500 数学训练题、2,488 代码训练题，dev 各 256、200 题。最新 checkpoint 的 16 个源码哈希与训练提交一致，v5 release 校验也通过。
- **Latent 调度。** 各教师前 10 次更新用最后三层隐藏表示监督，并逐步增加 top-16 token 蒸馏权重。全局第 21 步起只做 token 蒸馏，学生仍保留前 20 步更新。Pure top-16 从同一 Base R1 开始、全程只做 token 蒸馏。此前 token 首步尝试未完成正式对照；高显存观测没有确认 OOM。旧 OPD v3 用另一套 Qwen2.5 模型及目标，是历史结果。
- **固定结果快照。** 新加坡时间 11 月 14 日 **11:40:15**，完成 50/62 个 optimizer updates，数学第 51 步已生成 112/128 条。Drive `checkpoint-50` 已下载并按 manifest 逐项通过 **6/6** 载荷校验。五段日志各自的最后完整步为 21、30、43、46、50；拼接时需要按恢复基点和 attempt 去重。未见该 R1 实验的 dev/test 分数、匹配预算的纯 token 正式成绩或 62 步完成证据。随后在 11:45:03 通过 Colab SSH 复查，训练仍活跃，第 51 步已进入反传；固定快照继续用于下文复算。
- **恢复语义。** 第一次回到 checkpoint-20 后重算第 21 步，随后复用原会话第 22 步的 32 批轨迹；重算第 21 步的 grad norm 相差约 1.94e-5，权重一致性无法追溯。后续恢复日志中第 31 步可见 21 个复用批次，请核对它的直接父 checkpoint。11 月 14 日的 checkpoint-40 恢复只尝试使用第 41 步缓存，后续重新生成；截至固定快照第 41 步有两次恢复各复用 32 批，第 42–50 步均未观察到复用。这是本次操作上的约束，源码缓存键仍缺生成权重指纹。恢复过的主 run 仍需披露早期第 22 步疑点。
- **训练成本。** 旧复审对 28 个正常生成步骤估算两域各约 92% 时间用于生成。固定快照活跃指标的第 42–50 步内，正常生成的数学 4 步、代码 5 步，步耗中位数分别约 1,408 秒和 2,718 秒，按域累计生成占比分别约 92.49% 和 92.18%。样本较小，估算需给区间。 正式实验 62 步是对齐 LastOPD 的 7,936 条生成预算；论文没有报告默认方案 62 对 70 的比较。
- **PR #2 的实际边界。** EvalPlus 默认用 `vms-headroom-v1`，评测子进程以继承 VMS + 1 GiB 设置资源上限；容器资源与隔离配置见代码。早期在固定 Docker 镜像验证了两道真实 MBPP 样本。WSL 完整 pytest 199 通过、1 跳过，仓库及 v5 release 校验通过。完整 164/378 题重评分以及 runner 的缺失/不完整结果判定仍待做。旧 D0 的 GitHub 初次归档跳过两套官方评测；本机后来同一来源的候选已评分，HumanEval+ 77/164 = 46.95%，MBPP+ 209/378 = 55.29%。如未附本机明细，请将这两个数字标成我方核对而尚未从归档独立验证。资源协议不同的历史分数不能直接拿来证明当前 R1 增益。

### B. 审查评测代码，设计一轮足以判断 +5pp 的实验

1. 对比 PR #2 diff 与 EvalPlus 0.3.1 的 API、worker 生命周期和评分输出。优先追 `scripts/score_code_local_v3.py` 与 `scripts/evaluate_evalplus_v2.py`。检查 skipped、缺文件、非零退出、部分任务、已有输出被默认跳过、自动发布、重复任务和抽取语法错误。具体说明未完成应返回什么，单题候选不合法应如何记分，怎样识别评测基础设施故障。给最小补丁草案及可测试 fixtures。代码题始终在 Docker 内运行。
2. 给出 **Base R1 → Latent @40/50/62 → Pure top-16 @62** 的最小评测矩阵与次序。若 GPU 小时有限，预先锁定哪两个点先看并说明理由。在 `math_dev` 与 `code_dev` 上选择一个双域 checkpoint。最终 MATH-500、GSM8K、HumanEval+、MBPP+ 只用于锁定后的报告。数学同时保存 Math-Verify 与保守评分；代码分母、8 个 blocked dev 题、抽取失败及资源身份应有显式记录。
3. 比较 greedy 与 sampled，以及 8K 和 16K 上限。给出对三组一致、能够检测长度/截断偏差且成本可控的主协议。明确论文的 MATH-500 用法、MBPP+ 采样以及项目测试协议的差别。若要检验稳定性，给一个固定 seed/重复采样方案和预先锁定的切换条件。
4. 明确两组差值各回答什么：Latent−Base 是方案总收益；Latent−Pure 是整套隐藏层监督加调度的增量。若要隔离隐藏层监督，将相同 token ramp 的对照列为额外消融，并解释早期零权重与优化器步数如何处理。给逐题配对统计、计算功效或可检出区间，以及在 256/192 题上判断双域 +5pp 的局限。要求至少报百分点、配对区间、赢/输题数、截断率和每题输出长度。单 seed 要限定其结论。

### C. 决定 62、70、Pure top-16 和 math20 的顺序

1. 查论文附录 A 的 62 步来源，并区分附录 F 拉长到 120 步的 representation-only 批次组织消融。核对我们的 `steps` 属于 hard identity，checkpoint 保存 optimizer、scheduler、sampler、RNG，学习率为常数。给一个保留 checkpoint-62、明确写入父身份及 manifest digest 的 62→70 续跑路径。确认新增的八步不会恢复隐藏层训练。说明方案如何影响 62 步同预算比较。
2. 给出决策表，至少包括双域继续上涨、一域上涨一域下滑、两域持平、两域都下滑四类。针对每类明确是否先补 Pure top-16、修评测、做 62→70 或试 `math20`。每项给投入预算、结果需要超过什么门槛、何时回滚。根据当前中位耗时，八步约 4.6 G4 小时，估算应另计评测与中断。
3. 把用户目标 +5pp 拆成可定位的误差和真实能力候选：模板与抽取、超长或无 EOS、数学难度、代码函数与 stdin/stdout、教师相对 Base 的上限、负迁移。为每个解释指定判别数据和最小实验。只建议能够区分假设的训练改动。

### D. 决定先优化哪里

1. 复算两个域真实生成耗时、截断、token/s 和峰值显存。明确排除 spool 读取耗时和重复 attempt。批内长度占用只作代理，不能当作 FLOP 利用率。用每域中位和长尾给 wall time、G4 小时与中断回滚损失估计。
