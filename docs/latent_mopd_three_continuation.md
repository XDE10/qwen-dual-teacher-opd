# 延长阶段的完整断点保留：80步以后仍可继续

仓库入口为 `scripts/continue_latent_mopd_three.py` 与 `scripts/archive_latent_three_checkpoint.py`。它们尚未在GPU部署或运行。当前62步正式任务及其监督器保持原样。

## 到80步时保存什么

默认每5步保存并完成Drive归档，再继续下一段；显式指定的71等观察点额外保留。62→80默认保存65、70、75、80；如果指定先到71，则保存65、70、71。所有分段仍继承完整优化器和RNG，整体完成负责人指定的步数。

**不启用自动早停。** 验证集仅生成报告，验证下降不会自动停止、回滚或更换配方；是否追加预算由负责人决定。当前62步任务仍按固定62步完成。

每个完成的续训段都先保存完整 checkpoint，再执行`scripts/archive_latent_three_checkpoint.py`。保存范围包括学生权重、AdamW 的一阶与二阶矩和步号、优化器参数组、Python/NumPy/Torch/CUDA RNG、运行身份、生成参数、完整历史及排程。

归档另外保存实际运行源码、当前续训入口与归档入口、实际 pip freeze、GPU 信息，并将此前逐项核对的195文件重建包复制到该 checkpoint 的恢复目录。这样每个端点都能找到完整恢复材料，而不是只有最终推理权重。

Drive 使用独立远端 `p2drive:opd_runs/latent-three-extended-checkpoints/<运行身份哈希>/`。先上传完整断点并做 rclone check，再上传和核对恢复材料、核对重建包副本，最后才上传并读回 `checkpoint-80_verified.json`。上传失败或回执不一致时，不会写出本地“已验证”完成标记。**第80步恢复包目前尚未实际生成，这里描述的是已实现、等待实际运行验收的保存流程。**

不自动删除云端的62、71、80等已验证端点。继续训练时使用独立的新输出目录，上一段的完整端点保持原样。可重建包不是Colab整机镜像。

## 从80继续更久

新入口默认目标仍为80，但接受显式 `--target-step`，并允许以80或更晚的完整断点作为父断点。例如未来若dev仍上升，可从80派生到98，再从98派生到116。这里的后续目标只是说明恢复能力，没有启动或授权无限延长。

派生时继承全部优化器和随机数状态，保留三教师、数据、采样、损失、显存方案与教师计数。新运行只声明预算和输出目录的差异，并记录父断点哈希及完整父身份哈希。排程沿批准池原顺序追加，已用题目不重排、不重复；超出批准池会明确报错。每一段的终点都再次执行同样的完整归档。

未来在GPU环境中恢复好80断点及其完整日志后，可使用以下形式。下面是尚未执行的示例，父路径需对应实际恢复位置：

```bash
python -m scripts.continue_latent_mopd_three \
  --parent-checkpoint /content/restored80/checkpoint-80 \
  --target-step 98 \
  --output-root /content/runs/latent_three_extended98/full
```

该命令使用默认独立 Drive 归档路径。不会覆盖父80步目录，也不会从头训练。

## 实际验证范围

本地准备阶段运行10项CPU测试；仓库中的对应测试使用独立的合成输入，不依赖私人断点或已批准训练池。覆盖完整状态字段与AdamW矩缺失拒绝、上传失败和回执不一致时不接受完成标记、62→80排程、80→98排程前缀及身份继承、配方更改拒绝。CPU通过不代表真实80步恢复或GPU归档验收。正式任务到达相应端点后，还要核对真实文件和冷恢复。
