# 项目二：数学与代码双教师在线策略蒸馏

> 2026-10-24数据阶段：数学/代码文件身份与接口配额已纳入全量核对，数学train/dev、代码train/dev各10条真实样本已进入[人工审核包](<../reports/data_human_review_pack.md>)。参考实现通过沙箱源测试不等于逐题规格与测试覆盖已经终审；不能写“98%完成”或只凭20条预览宣布全量合格。原生数据保持不变，human_review仍pending。用户确认数据后再进入训练脚本阶段，本轮没有启动或编写GPU训练入口。

版本：2026-10-23（数学提示词契约固定；代码 v2 数据身份保持）。性质：数据工程已推进，模型训练待实施。以原始 1.5B 学生为统一起点，研究能力迁移与领域保持，不把恢复旧 SFT 损失等同于超越原模型。

## 1. 项目目标与边界

学生自己生成回答，教师对学生走过的前缀给出分布，学生据此更新。这是 on-policy distillation（OPD）。先完成单教师，再用已知领域标签选择数学或代码教师。

研究问题：数学单教师是否影响代码能力；混合数据和专业教师分别贡献多少；双教师收益是否值得教师评分与搬运成本。

首版不做学习型路由、熵融合、长度奖励或多卡部署。它是多教师领域路由 OPD，不宣称完整复现某篇 MOPD 论文；若后续采用论文实现，要单独核查其目标函数与实验差异。

交付：词表对齐审计、在线 rollout→教师评分→学生更新代码、五个学生状态、双领域基准结果、成本分析及完整恢复记录。

## 2. 模型配置

- 学生：`Qwen/Qwen2.5-1.5B-Instruct`，各核心组从同一 revision 开始。
- 数学教师：`Qwen/Qwen2.5-Math-7B-Instruct`。
- 代码教师：`Qwen/Qwen2.5-Coder-7B-Instruct`。
- 混合领域单教师基线：`Qwen/Qwen2.5-7B-Instruct`，分时使用，不要求四模型同时驻留。
- 项目一的数学检查点：后续替换数学教师的单独实验，先评测证明合适，不能只因自己训练就认定更强。
- 学生 BF16 LoRA rank 16、alpha 32，学习率起始 `5e-6`，梯度检查点开启。正式参数由 dev/pilot 确定。

教师 `eval()`、冻结参数、禁用梯度；这不消除前向激活、logits、KV cache。首选 A100 80GB，40GB 需重新测量。按领域连续小块处理，减少逐 batch 换教师的搬运开销。

## 3. 第一项必须完成的工程：词表对齐

官方配置中学生 `vocab_size=151936`，代码教师为 `152064`，不能直接对整个 logits 矩阵逐列计算 KL。

实施步骤：

1. 下载各 tokenizer、added tokens、config，记录哈希。
2. 比较 token 字符串→ID 映射、特殊 token 和实际编码行为。
3. 查清输出矩阵额外行是有效 token 还是填充行，不能仅按行数裁切。
4. 只有在有效 token 与前缀编码可对应时，定义共同支持集、mask 和概率重新归一化规则。
5. 对数学、代码、Unicode、空格、特殊符号等至少 50 个输入验证编码对齐。
6. 若有效分词序列不兼容，暂停逐 token KL 实现，改选兼容教师或设计跨 tokenizer 方法，不能假装索引一致。

输出 `tokenizer_alignment_report.json`，列出不匹配 token、处理规则与尾部概率质量。共同支持集蒸馏不完全等于原始全词表目标，报告中说明。

2026-10-23已复验：四个固定revision的完整token→ID映射一致，64个数学/代码缩进/Unicode/特殊符号样本裸文本编码全部一致，共同有效ID为0～151664（151665个）。学生config输出151936行，三教师152064行；仅这些快照可裁切 `[..., :151665]`，再分别以FP32 log_softmax重新归一化。生成采样之前也要屏蔽支持集外行。Math教师独立chat template与学生不同，必须只用学生冻结模板渲染一次，将同一token-ID前缀送给所有教师，不能独立套模板后逐位置比较。原报告保留，当前离线证据见 `reports/tokenizer_alignment_revalidation_20261023.json`；真实模型尾部概率质量和GPU前向尚未验收。

**裁切优化的准入条件：** 本轮核查的学生和 Coder `tokenizer_config.json` 均包含 ID 到 151664 的 added tokens，但这不能单独证明全部基础词表、合并规则与 Math 教师相同。只有固定 revision 的完整 tokenizer 审计证明有效 ID 连续且语义一致，才把映射简化为前 N 列切片。N 由审计生成，不硬编码 151665；`min(V_student,V_teacher)` 只解决形状问题，可能保留无效输出行，不是正确性的替代证明。生成与评分阶段也应一致屏蔽确认无效的行，并记录裁切前被移除的概率质量。额外矩阵行的存在不自动证明其概率恒为零。

### 3.1 数学提示词与学生轨迹接口契约

正式配置为 `project_blueprints/configs/project2_prompt_contract.json`，版本 `project2-prompt-v2-20261023`。数学任务显式传入共同 system 消息：

```text
Please reason step by step, and put your final answer within \boxed{}.
```

这是 [Qwen Math 官方 CoT 用法](https://huggingface.co/Qwen/Qwen2.5-Math-7B-Instruct#usage) 中的 system 指令，不把它的存在解释成准确率保证。学生、Math 教师以及数学域通用教师基线使用同一条指令；题目原文放在 user 消息，不附参考答案。学生 tokenizer 只渲染一次，并保留生成 assistant 前缀。生成后的完整 `input_ids`、`attention_mask` 直接交给教师 forward；如需换设备，仅迁移张量，不允许教师 decode/re-encode、另套模板、追加答案前缀或替换 EOS。

可执行 CPU 接口为 `src/teachers/opd_contract.py`：核验学生生成前缀、共同有效 ID 范围、连续的非 padding 区间和响应目标 mask；支持左右 padding，首版不支持 packing。保留学生实际生成的 EOS；位置 t−1 的 logits 预测目标 token t，prompt 和 padding 不进入 KL。共同支持集由固定 tokenizer 审计读取，采样前屏蔽无效输出行，双方在有效支持集分别执行 FP32 log_softmax。这个接口不是完整 OPD trainer。

数学输入预算保持本项目原定值：总上下文 4096、最多生成 1024；这不同于项目一的 RL 2048，不在本轮混改。代码域保持已封存 v2 的 user-only 学生默认 system/template、生成预留 1536，不把数学指令加入代码题，也不重新封存代码数据。

离线验收入口 `python -m scripts.audit_project2_prompt_contract`，报告 `reports/project2_prompt_contract_audit.json`。64 个固定数学/代码/Unicode/特殊符号探针在四个 tokenizer 的显式数学 system 下编码一致；实际数学训练 2500 题、共同 dev 256 题的输入预算单独复核。独立渲染各 tokenizer 只用于这项诊断，生产教师路径不调用模板。真实教师前向、尾部概率质量、提示词对准确率/输出长度的影响仍需 GPU 验收。

D0、全部学生组、数学教师参考评测必须记录同一提示版本。历史不同提示的分数不直接对比；小规模提示词对照只用 dev，不据最终测试成绩反向选提示。

## 4. 数据集配置

### 4.1 数学 prompt 池

目标 2500 道：GSM8K train 1000 道＋MATH-lighteval train 1500 道。沿用项目一的题目 ID、来源、去重与 dev 排除机制。只给学生题目，不把标准答案放进生成 prompt。

2026-10-23 修订：数学 dev 必须直接复用 `data/math/math_dev.jsonl` 的同一 256 个 ID 及文件哈希；MATH 训练抽样从 `data/math/math_train.jsonl` 的 7184 题候选池进行，不重新划 dev。GSM8K 也从已封存 train 取样并检查与共用 dev/test 的重叠。共享 dev 仅是共享开发协议，不是独立最终测试，也不代表 100% 无污染。当前 dev 题面、错题和改写不能成为训练或合成种子。

标准答案用于能力评测和轨迹质量诊断，不默认用于筛除所有学生错误轨迹；错误轨迹上学习教师分布也是 OPD 的一部分。若增加正确性过滤，作为独立实验。

### 4.2 代码 prompt 池

v1 首轮选择带验证信息的 `open-r1/verifiable-coding-problems-python` 作为统一候选池，以下保留其诊断记录；当前 v2 路线见第 4.2.1 节。该来源公开字段包括 `problem_statement`、`gold_standard_solution` 和 `verification_info.test_cases`。先核查测试类型与参考实现，再按原题/来源 ID 去重和分组划分，封存 200 道 dev，剩余候选中选最多 2500 道训练题。不能把含重复题的行随机切开当作独立划分。

首版修订为显式分类 `stdin_stdout`、独立函数 `function`、`Solution` 实例方法 `solution_method`；不再只筛 stdin/stdout。分别核查所有测试用例的 type/fn_name、参数序列化、入口与参考代码 AST，不能只看第一条 fn_name，也不假设有顶层 starter_code。代码题中 def solve() 可能仍是 stdin 程序，不能用 def 正则代替接口判定。交互、自定义 checker、多合法输出、缺测试、复杂对象接口和外部文件依赖首轮隔离。

训练目标仍为最多 2500 题，可先以函数调用题约 50% 为配比候选（独立函数与类方法分别报告）；实际数量不足则报告缺口，不重复少量题凑比例。代码 dev 的 200 题按接口分层封存，训练与 dev 都保留函数签名及输入/返回约定；HumanEval+/MBPP+ 严格沿用原工具函数协议，不把类方法和独立函数混为完全一致。参考代码只静态解析不执行时，产物必须标为结构候选；只有隔离沙箱运行和测试审核通过后才称执行验收。竞赛难度、训练接口和 EvalPlus 的差异都需报告，不预言一定零分或必然泛化。

`deepmind/code_contests` 可作为备选，它提供 public/private/generated tests，但存在不同来源、语言与判题约定，仍要适配和去重。AceCode、Code-Contests-Plus 留作候选，不在没有字段、许可和运行核验时宣称可直接替换。

2026-10-23 首轮真实筛选：固定快照共 35735 行，其中 stdin/stdout 35537 行、标为 function_call 的仅 198 行。全部用例初筛仅 4 道独立函数候选；额外字面量诊断又隔离 1 道“整数输入被参考程序直接按字符串遍历”的明显冲突。重分组后训练 2500 道（stdin/stdout 2498、独立函数 2、Solution 方法 0），dev 200 道（stdin/stdout 199、独立函数 1、Solution 方法 0）。这证明当前来源无法支撑 50% callable 配比，不能宣称已经解决接口覆盖；后续补充函数题来源须另做许可、接口和去重审计。当前产物仍待隔离执行和抽检，不直接用于报告 dev 执行正确率。

脚本入口为 `src/data/screen_code_interfaces.py`，附加窄范围诊断为 `scripts/quarantine_code_literal_conflicts.py`；产物位于 `data/project2_code/`，完整复现命令、来源版本、哈希和未通过原因见 [本轮执行报告](<../reports/data_screening_20261023.md>)。项目二数学池已从共用封存文件取 MATH 1500＋GSM8K 1000，数学 dev 未另划。

保留低成本替代路线：从 Magicoder 或 CodeFeedback 自动筛选 Python prompt，OPD 训练本身不需要测试或标准答案；代码 dev 仍使用上述带测试来源，并明确训练/dev 分布差异。`def` 正则只能粗筛：可能漏掉 stdin 程序，也可能把解释文本当任务；再结合语言字段、结构检查和抽样审核，不能仅凭正则认定题目有效。

**人工工作改为抽检，而非从零写 200 套测试：** 自动跑所有 dev 的参考实现，分层抽查 30～50 道题的输入输出约定和测试覆盖；人工修订的成本设上限，复杂问题先隔离。任何参考实现与学生代码都在第 8 节的隔离执行环境中运行。训练端只接收 prompt，不暴露 dev 测试、参考代码或隐藏用例。

### 4.2.1 原生函数数据 v2：先小样本验收，再批量构建

原始 `data/project2_code/` 保留为 v1，独立输出 `data/project2_code_v2/`。目标为代码训练 1250 道 stdin/stdout＋1250 道独立函数，dev 100＋100；不把 `Solution` 方法混记为独立函数。数学池和数学 dev 不重新划分。v2 各实验组共享同一版开发集，不能比较 v1/v2 不同题目上的总分来宣称模型进步。

新增来源固定为 `TIGER-Lab/AceCode-87K`（revision `13216309a9f6cb40b60cb1a9750071efeac414ad`）与 `ise-uiuc/Magicoder-OSS-Instruct-75K`（revision `5f839b1f368a76b161028bb9edff055db34022b2`）。AceCode 没有统一金标参考解答或标准 entry_point 字段；从题面、assert 调用和候选实现联合确定入口，源 `pass_rate=1` 只作筛选线索。Magicoder 先按 Python 字段筛选，再核对题面明确命名的目标函数，不能只找任意顶层 def。

小样本各50条，最终保留Ace6条、Magicoder8条；Codex agent审阅后隔离8条已观察到的规格冲突，不称人工审阅。Ace6条在隔离容器中通过全部源断言和两类常量错误实现诊断。接口与去重回归检查10项通过后封存 `data/code_v2_pilot/report.json`；批量入口校验该 gate、规则及保护文件哈希，规则变更须重新验收。

函数训练题优先使用通过静态接口筛选的Ace，Magicoder作为备用；OPD训练不要求每题都有测试，训练文件仅含prompt和接口，不包含参考代码、隐藏用例或正确性标签。题面明确签名与参考参数冲突、print/None契约冲突、类/异步入口、复杂对象、外部依赖、动态执行等先隔离。v2开发候选仅支持已核验的普通参数与独立函数，复杂测试表示不自动猜测转换。

函数dev至少3组不同输入，参考程序须通过每条源断言，并拒绝返回None及固定首个期望值的错误实现；stdin/stdout dev从旧dev及从未训练的v1 prompt中重新封存，每题至少3例，按空白分词后的精确stdout比较运行全部已有用例，每题总预算20秒。失败或超预算保留原因，不删除难例来给某个学生提分。200题的执行证据不证明全部测试符合题意或覆盖充分；全量规格/覆盖审核仍是后续质量门槛。

## 5. 目标函数与数据流

学生策略为 p，教师为 q。在学生生成前缀 h 上，第一版使用共同有效词表上的完整 reverse KL：

$$D_{KL}(p\|q)=\sum_v p(v\mid h)[\log p(v\mid h)-\log q(v\mid h)].$$

完整流程：学生生成轨迹并保存 → 在相同前缀上计算教师 log-prob → 学生重新前向计算带梯度分布 → 只对回答有效 token 求损失 → 更新学生 → 丢弃过期 rollout 或按明确缓存窗口管理。

- 教师没有梯度；学生 rollout 采样过程本身不反向传播。
- 必须检查 next-token shift：位置 t 的分布预测下一个 token，不是当前位置已输入的 token。
- prompt、padding 不计入回答损失；EOS 的处理明确固定。
- 每个 rollout 首版只做一次更新，减少陈旧策略偏差。
- 第一版温度 T=1；若加温度平滑，要明确 loss 缩放与各组一致性。
- 这是在采样前缀上计算条件 KL 的实用目标，不应把任何忽略状态分布梯度的实现都称为完整轨迹目标的精确梯度。

不要把单条采样 token 的 `log p-log q` 直接求导当成完整分布 reverse KL；采样估计涉及额外梯度处理，应另行推导。

### 5.1 PyTorch 数值参考实现

以下用于小张量正确性验证，不是已经验收的全长显存优化实现。输入 logits 尚未 shift，形状为 `[batch, sequence, vocab]`；`response_mask` 与输入 token 对齐。两个索引数组来自词表审计，按相同 token 语义排序。教师前向本身也必须放在 `no_grad()` 内，而不是只在 loss 阶段 detach。

```python
import torch
import torch.nn.functional as F

def reverse_kl_loss(student_logits, teacher_logits, response_mask,
                    student_ids, teacher_ids):
    student_scores = student_logits[:, :-1].index_select(-1, student_ids).float()
    teacher_scores = teacher_logits.detach()[:, :-1].index_select(-1, teacher_ids).float()
    if student_scores.shape != teacher_scores.shape:
        raise ValueError("Aligned distributions must have the same shape")
    valid_mask = response_mask[:, 1:].bool()
    if valid_mask.shape != student_scores.shape[:2]:
        raise ValueError("Response mask does not match shifted positions")
    if not valid_mask.any():
        raise ValueError("No response tokens in this batch")
    student_scores = student_scores[valid_mask]
    teacher_scores = teacher_scores[valid_mask]
    log_student = F.log_softmax(student_scores, dim=-1)
    with torch.no_grad():
        log_teacher = F.log_softmax(teacher_scores, dim=-1)
    token_loss = (log_student.exp() * (log_student - log_teacher)).sum(-1)
    if not torch.isfinite(token_loss).all():
        raise ValueError("Non-finite reverse KL")
    return token_loss.mean()
```

学生概率不能 detach，否则梯度目标改变。FP32 的 log-softmax 与归约用于提高稳定性；索引须位于对应 logits 设备，选取后两份分布需在同一 loss 设备。有效支持中不应混入已被置为负无穷的无效列，以免 `0 * NaN`。跨 micro-batch 或分布式训练要按有效 token 数聚合，而非盲目平均不同长度 batch 的均值。

验收用例：相同分布 KL 近零且学生梯度近零；不同分布学生有有限梯度、教师无梯度；padding 不影响结果；空回答明确失败；置换教师词表后经映射结果不变；FP32 参考与小型双精度梯度检查一致。此代码增加 FP32 和索引副本，长序列生产实现仍需单独优化峰值。

## 6. 显存、Top-K 与在线性的区别

完整 logits 大小近似 B×L×V×每元素字节。即使 B=1、L=2048、V 约 152k，单份 BF16 logits 也约 0.62GB（十进制），再加 FP32 概率、教师/学生及梯度会明显放大。

先用短序列验证完整 KL，再研究序列分块、loss 融合或教师 CPU 缓存。仅在 logits 已完整分配后切片，并不能避免此前的峰值。

Top-K 是选做近似：必须存 token IDs、概率和尾部质量，定义共同支持上的处理，比较其与完整 KL 的误差。缓存当前学生 rollout 的教师结果仍可服务在线训练；预先缓存固定数据并长期训练则不能称为严格 on-policy。

首轮生成上限建议数学 1024、代码 1536，最长总上下文 4096；按实际截断决定扩展。最终评测统一使用每领域固定预算，不因某模型差就单独给更多 token。
